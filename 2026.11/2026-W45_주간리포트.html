기획서가 사라진 개발팀은 어떻게 일해야 할까?

수께끼수

기획서와 목업만 AI로 바꾼 두 번의 시행착오 뒤 새 팀에서 직렬로 넘기던 순서부터 걷어 낸 병렬 개발

수께끼수는 20명 남짓 게임 개발팀에서 상부 지침에 따라 기획서를 AI로 써 보고 이어 바이브코딩 목업으로 기획서를 대신해 봤지만, 첫 시도는 작업량이 예전과 비슷해졌고 두 번째 시도도 기존 기획서 기반 파이프라인과 크게 다르지 않았다고 돌아봅니다. 넘기는 결과물만 AI로 만들어서는 파이프라인이 바뀌지 않는다고 결론 낸 필자는 조직 개편 뒤 10명이 채 안 되는 팀에서 기획을 기다리는 직렬 흐름을 없애고, 깃 워킹트리와 클로드 코드 세션을 연동한 팀 내부용 소규모 인트라를 직접 만들었습니다. 필자는 이 구조로 통상 워킹데이 닷새쯤 걸린다고 가늠한 마일리지·멤버십 개발을 사흘 만에 파트별 테스트까지 마쳤다면서도, 겹치는 부분의 충돌과 툴 유지보수 문제가 있었고 사용자와 직접 닿는 끝단은 여전히 스페셜리스트의 몫이라고 덧붙입니다.

핵심 포인트

  • 필자는 직군 경계가 흐려져도 대규모 서비스는 여전히 파트를 나눠 일하고, 그 사이를 잇던 기획서·명세 방식에서는 파트마다 다른 것을 떠올리는 데다 병렬로 일할 수 없어 불협화음이 끊이지 않았다고 말합니다. 20명 남짓 게임 개발팀에 기획서를 예전 방식으로 쓰지 말고 AI를 쓰라는 상부 지침이 내려오자, 팀은 AI에게 코드베이스를 읽히고 기획안을 크로스체킹해 기획서를 뽑았고 시인성을 잡고 오탈자를 고치는 후보정 시간은 획기적으로 줄었습니다. 그러나 문서는 불필요한 텍스트와 읽히지 않는 표, 왜 있는지 모를 코드 설명으로 길어지기만 해 팀원들의 거부감을 샀고, 이를 고치려고 하네스를 만들고 지침을 세우고 프롬프트를 다듬자 작업량이 예전에 문서를 쓰던 것과 비슷해졌습니다. 손으로 쓸 때 파트 안 검수에서 잡던 예외 케이스도 놓쳐, 장비 강화 예시에서는 재화를 차감한 시점에 앱이 종료될 때의 재화 처리와 결과 확정, 재접속 때 알릴 내용이 빠졌고 결국 필자가 문서를 직접 고친 뒤 마무리 보정만 AI에게 시켰습니다.
  • 다음 시도로 팀은 기획서 대신 바이브코딩으로 만든, 실제로 돌아가는 목업을 쓰기로 했고 목업은 그럴듯했으며 만드는 재미도 올라가는 듯했습니다. 하지만 기획 파트는 기획 의도나 '왜'라는 질문 대신 바이브코딩 잘하는 법을 연구했고, 프로그램과 아트 파트도 코드를 효과적으로 짜거나 아트 퀄리티를 올리는 대신 목업 기반 개발을 위한 AI를 공부했습니다. 깊어질수록 프로그램 파트는 목업을 해석해 AI가 만든 엉성한 스파게티 코드를 다시 고쳤고, 아트는 목업을 다시 디자인 언어로 옮기며 레퍼런스를 직접 그렸으며, 공부한 AI 솔루션은 모델 업데이트에 따라 무용지물이 돼 지식 자원으로 남지 않았습니다. 필자는 두 경험에서 넘기는 것을 AI로 만드는 정도로는 껍데기만 AI 활용일 뿐이라고 결론 내리고, 같은 순서로 일하면서 그 안의 도구 몇 개만 바꾸면 나아질 거라 여긴 것을 이유로 꼽습니다.
  • 조직 개편 등을 거쳐 새 프로젝트에 착수하며 10명이 채 안 되는 작은 조직이 된 필자의 팀은 킥오프에서 AI 시대에 왜 이전과 같은 제작 파이프라인이 필요한지를 이야기한 뒤, 프로그램과 아트가 기획을 기다리는 흐름부터 없앴습니다. 무엇을 만들고 무엇이 목표인지만 빠르게 정한 뒤 기획은 여러 세션을 띄워 기획서 대신 직접 제품을 만들고 필요한 피처만 md 등으로 정리해 워킹트리에 공유했으며, 같은 작업을 기획과 프로그램이 동시에 진행하다 충돌이 나면 각자의 의도를 공유하고 병합 방법만 논의했습니다. 팀에는 우리가 만드는 것의 목적을 항시 명심할 것, '어떻게 해요'가 아니라 '뭐가 더 나아요'라고 말할 것이라는 두 원칙을 적용했고, 각 파트는 경계 대신 교집합과 차집합으로 역할을 재분배했습니다. 마일리지 수치도 기획자가 엑셀에 식을 엮는 대신, 예컨대 1회당 10마일리지와 사용처·획득처를 알려 주고 보유 최대치가 약 100만 원 값어치가 되도록 맞추는 수식을 코드로 넣어 달라고 LLM에 위임했습니다.
  • 필자는 예전 같으면 만들었을 담당 개발진 단체 채팅방 대신 팀원만 접근하는 소규모 인트라를 항목 단위로 만들었고, 프로젝트 전체를 담으면 무거워진다며 모듈화해 두면 누구나 복사해 쓸 수 있어 유지보수 부담도 없다고 말합니다. 노션 같은 협업 문서 도구를 쓰지 않은 이유로는 실제 코드와 깃 워킹트리를 바로 임포트할 수 없다는 점을 듭니다. 깃 워킹트리를 연동하고 프론트엔드를 맡은 기획과 개발이 클로드 코드 세션을 페이지에 연결하면, 하네스가 세션의 아웃풋을 인트라에 자동으로 렌더해 dev 환경을 열지 않고도 돌아가는 목업을 볼 수 있습니다. 여기에 목업을 관리하는 세션과 엔진·데이터 등 실제 코드를 다루는 세션을 연결해 목업에서 나온 수정 사항을 코드베이스에서 검토하고 그대로 고치게 했고, 필자는 앞선 시도의 변환 작업이 목업과 실코드가 떨어져 있던 탓이라 보고 둘을 붙이자 그 작업이 없어졌다고 말합니다.
  • 필자는 게임에서 마일리지·멤버십을 개발한다고 치면 통상 기획안 작성 이삼 일, 컨펌 반나절, 개발 리뷰 후 착수까지 반나절, UI 이틀, 서버 하루 반, 클라이언트 하루가 들어 서로 겹치는 시간을 감안하면 대략 워킹데이 닷새가 걸린다고 설명하고, 이것이 기획 단계가 밀리지 않을 때의 최적 코스이며 이번에는 팀의 전공인 게임이 아닌 앱 개발이었다고 덧붙입니다. 새 구조에서는 기획자가 바이브코딩한 레퍼런스와 변형이 실시간으로 워킹트리에 올라가 인트라에 렌더되고, 엔지니어와 디자이너가 그 화면에서 의도와 기술적 리스크, 자기 할 일을 정리해 각자 착수하면서 누구도 선행 작업을 기다리지 않았고 회의도 필요하지 않았다고 적습니다. 결과는 첫날 기반 작업, 둘째 날 실제 dev 환경에 올라갈 작업, 셋째 날 파트별 테스트까지였고, 필자는 겹치는 부분의 충돌과 툴 유지보수 문제가 있었으며 이게 정답이라고 생각하지도 않는다고 밝힙니다.

실무 시사점

필자의 두 실패가 함께 보여 주는 것은 AI가 산출물을 빨리 만들어도 그것을 받는 쪽의 일이 그대로면 시간이 다른 곳으로 옮겨 갈 뿐이라는 점입니다. 기획서를 AI로 쓰자 아낀 후보정 시간은 하네스와 프롬프트를 다듬는 시간으로 돌아갔고, 목업을 AI로 만들자 개발과 아트가 그 목업을 자기 언어로 다시 옮기는 일을 떠안았습니다. 팀의 AI 도입을 점검한다면 파트마다 AI를 쓰는지보다 누가 무엇을 기다리고 누가 남의 결과물을 다시 고쳐 쓰는지를 보는 편이 이 글의 진단에 맞습니다. 필자의 설명대로라면 세 번째 구조에서 일정을 줄인 것도 생성 속도라기보다 파트 사이의 대기와 변환 단계를 없앤 데서 나왔습니다. 목업 세션과 실코드 세션이 이어지고 모두가 같은 화면을 보게 되자, 기획 의도를 문서로 옮기고 그 문서를 다시 코드와 시안으로 옮기던 단계가 사라졌습니다. 대신 비어 있을지 모르는 자리도 있습니다. 첫 시도에서 필자가 아쉬워한 것은 파트 안 검수에서 예외 케이스를 잡던 과정이었는데, 세 번째 구조에서 그런 예외 검토를 누가 어느 단계에서 맡는지는 본문에 따로 적혀 있지 않습니다. 엔지니어와 디자이너가 인트라 화면에서 기술적 리스크를 정리한다는 대목과 사용자와 닿는 끝단은 스페셜리스트가 해야 한다는 마무리가 그 자리를 가리키지만, 파트 안 검수가 하던 일을 화면 위 조율이 얼마나 대신하는지는 이 사례만으로 알기 어렵습니다. 10월 16일에 올라온 이 글은 이번 주 처음 인기 풀에 들어 5위(조회수 9,204)에 올랐고, 이번이 첫 분석입니다. 원본 flags는 develop·ai인데, 모델 자체를 소개하기보다 /compact·/effort·/mcp 같은 명령과 CLAUDE.md 분량, 서브에이전트 모델 지정처럼 클로드 코드로 개발하는 작업 흐름을 손보는 글이라, 클로드 코드 활용 팁을 develop으로 둔 3907(W38·W41)과 3931(W40·W42)의 선례를 따라 develop으로 분류했습니다. 해시태그 '클로드코드'에 근거한 claude-code는 W44까지 42회(고유 기사 27건)로 관측 16개 주 전부에 붙었고, 본문이 클로드 코드의 명령과 설정을 구체적으로 다뤄 이번 주 3위 3997과 함께 붙으며 17번째 주에도 이어집니다. 실무 시사점

같은 /compact라도 자리를 뜨기 전에 돌리느냐 쉬고 와서 돌리느냐에 따라 캐시에 다시 써야 할 양이 달라집니다. 오스마니가 캐시를 새로 쓰게 만드는 행동으로 꼽은 여섯 가지에는 모델 변경과 대화 컴팩트처럼 결국 해야 하는 일도 들어 있어, 재작성을 아예 없애기는 어렵습니다. 그래서 그의 조언을 모아 보면 재작성을 피하라는 말보다 몰아서 치르라는 말에 가깝습니다. 빠른 모드와 MCP 구성은 세션 첫머리에 정해 두고, 모델을 바꿀 때는 직전 매듭에서 컴팩트를 먼저 해 새 모델이 다시 써야 할 대화를 줄이며, 컴팩트 자체도 캐시가 살아 있는 동안 끝냅니다. 여럿이 클로드 코드를 쓰는 팀이라면 세션 도중의 설정 변경을 취향 문제가 아니라 비용이 붙는 행동으로 함께 알아 두는 편이 낫습니다. W44에 분석한 3964(9월 23일 게재)는 앤트로픽이 에이전트·코딩 비용의 대부분이 캐시 읽기라며 캐시 가격을 60% 내렸다는 공급사 쪽 소식을 전했는데, 이 글은 같은 칸을 사용자 쪽에서 비춥니다. 단가가 내려가도 그 혜택은 캐시가 유지될 때만 닿고, 유지 여부는 휴식 길이와 세션 중 설정 변경 같은 습관이 가릅니다. 3964가 전한 오픈AI의 조치, 곧 추론 강도나 사용 도구를 바꿔도 기존 캐시가 유지되게 한 변화와 견주면, 10월 16일 게재 시점의 클로드 코드에서는 구독·API 키 기준으로 추론 강도 변경은 캐시를 지우지 않지만 사용 도구가 바뀌는 MCP 서버 연결·해제는 캐시를 새로 쓰게 합니다. 아마존 베드록이나 구글 클라우드 에이전트 플랫폼처럼 클라우드 제공자를 거쳐 쓰는 팀은 캐시 수명이 5분인 데다 추론 강도 변경도 캐시를 지우는 조건이라, 같은 습관의 차이가 구독 사용자보다 크게 돌아올 수 있습니다. W43 3959는 9월 22일 게재 시점 기준으로 Claude Max의 5시간 세션 한도와 주간 한도의 2중 구조, 그리고 한도를 넘기면 API 종량제로 토큰을 더 받아 쓰는 운용을 전했습니다. 이 글은 구독자도 추가 사용 크레딧을 쓰기 시작하면 캐시 수명이 1시간에서 5분으로 줄어든다고 적는데, 이 크레딧이 3959가 말한 종량제 전환과 같은 장치인지는 본문에 나오지 않습니다. 그 사이 조건도 바뀌었습니다. W44 3964(9월 23일 게재)는 앤트로픽이 5시간 한도를 상향하고 리셋 기능을 넣었다고 전했고, W43 3959 카드가 같은 주 3982를 들어 적었듯 10월 9일 게재 주부터는 Max 구독자에게 매달 API 크레딧(Max 5x 100달러, Max 20x 200달러)이 지급됩니다. 그렇더라도 추가 사용 크레딧을 쓰는 동안에는 자리를 5분 넘게 비우기만 해도 캐시를 새로 써야 하니, 쉬기 전 컴팩트가 가장 값을 하는 때는 오히려 그 구간일 수 있습니다. 추론 강도에서는 시히파의 수치가 판단 순서를 정해 줍니다. 최대로 올리면 시도당 토큰 중앙값이 7만 3천에서 22만 2천으로 커지는 사이 통과는 140회에서 214회로 늘었지만, 절차가 정해진 운영 작업처럼 상승 폭이 작은 영역도 있었습니다. 결과가 빗나갈 때 강도부터 올리지 말고 검사 수단과 정보·권한이 빠졌는지 먼저 보라는 글의 조언은, 막힌 원인이 실수인지 능력 밖의 일인지를 먼저 가르라는 말로 읽힙니다. 이 글의 숫자는 출처가 한쪽에 몰려 있다는 점도 알고 쓰는 편이 좋습니다. 토큰 수치는 클로드 코드를 만드는 회사의 엔지니어가 자기 제품으로 실험한 결과이고, Terminal-Bench 3.0 분석은 Fable 5.1 한 모델로 낸 것입니다. 280만·175만 토큰은 턴 수의 차이를 보여 주려는 계산 예시이며, 필자는 습관을 바꾼 전후의 사용량을 내놓지 않고 자기 /usage 화면에서 클로드 코드가 긴 문맥과 서브에이전트를 원인으로 짚었다는 데서 멈춥니다. 본문 역시 두 엔지니어의 글을 필자가 옮겨 정리한 것이라 원문의 맥락이 줄었을 수 있고, 명령어·캐시 수명·모델 이름은 모두 게재 시점의 클로드 코드 기준이므로 지금 쓰는 버전에서 같은 동작인지 확인하고 적용하는 편이 안전합니다.

  • 필자는 2026년 벤더 발표문의 이름부터 비교합니다. 마이크로소프트는 Foundry IQ를 '기업 데이터를 위한 관리형 지식 계층'으로 정의하지만 최상위 이름은 intelligence layer이고, AWS는 Semantic Layer를 최상위 용어로 두고 Knowledge Layer를 그 안의 한 층으로 쓰며, Snowflake는 Horizon Context를 거버넌스가 적용된 컨텍스트 레이어로, Forrester는 context layer로 부릅니다. 제품 자체를 knowledge layer로 정의하는 곳은 Foundry IQ뿐이라 필자는 아직 업계 표준 용어로 부르기 어렵다고 봅니다. 반면 지표와 온톨로지를 적는 형식은 2025년 9월 17개사가 출범시킨 Open Semantic Interchange가 2026년 7월 8일 Apache 인큐베이터에 받아들여져 Apache Ossie (Incubating)로 이름을 바꾸며 한 규격으로 모이고 있는데, 범위는 지표·차원·관계·비즈니스 규칙이고 검색·권한·최신성은 묶지 않습니다. 원문을 확인한 여섯 곳의 2025년 9월 이후 신규 제품·객체 이름에 RAG가 하나도 붙지 않았다는 관찰도 덧붙입니다.
  • 필자는 이 문제가 검색이 부족해서 생긴 게 아니라고 선을 긋습니다. 사람이 결과를 직접 보던 때는 반년 전 정책 문서나 남의 팀 문서를 보고 넘겼지만, 자율 에이전트에는 그 전제를 둘 수 없어 시스템이 대신 걸러야 한다는 것입니다. 정합성에서는 Snowflake 사내 컨텍스트 레이어 경험의 '활성 고객' 질문을 듭니다. 한 팀은 credits_consumed > 0 and account_type != 'TRIAL'로, 다른 팀은 리전 조건 없이 COUNT(DISTINCT account_id)로 세어 SQL은 둘 다 돌지만 숫자가 다릅니다. 필자는 'XX시트가'처럼 조사가 붙은 질의가 색인의 원형 토큰을 못 잡는 문제를 질의 쪽 접두사 확장으로 먼저 풀고, 놓치는 경우를 색인·질의 양쪽의 한글 bigram 분절로 메웠습니다. 최신성에서는 Glean이 변경을 웹훅으로 보통 1~5분 안에 처리하고 놓친 변경은 24시간 주기 증분 크롤러로 모으며 그 대상에 권한도 든다고 전합니다. 필자는 임베딩이 시간을 모른다고 보고 날짜를 검색 조건과 랭킹용 메타데이터로 뺐고, 시점이 박힌 질의에만 검색 전 하드 필터를 걸되 표현을 해석하지 못하면 필터 없이 통과시킵니다.

  • AWS 가이드에서 Knowledge Layer의 내부는 원본을 옮기지 않고 그래프처럼 질의하게 하는 Virtual Knowledge Graph, 온톨로지와 인스턴스 데이터를 저장하는 Neptune, 추론기와 규칙을 처리하는 Symbolic Reasoning, 지표 정의를 담는 Metric Store 네 덩어리를 조립한 구조입니다. 필자는 W3C OWL 2 정의상 온톨로지가 classes·properties·individuals·data values로 이뤄진 정밀한 서술문의 집합이고 검색·권한·실행은 그 정의 안에 없다고 짚습니다.   • 필자는 그래프만 세팅하면 강력한 컨텍스트가 생긴다는 근거가 생각보다 약하다며, 단순 사실 검색에서 기본 RAG가 GraphRAG와 비슷하거나 낫다는 GraphRAG-Bench의 관찰, 인덱싱 구축 시간이 커뮤니티 기반 GraphRAG 5,560초 대 일반 RAG 135초였다는 체계적 평가 논문, 무관한 질문과 평가 편향이라는 두 결함을 짚고 편향을 빼면 이득이 훨씬 온건해진다는 연구를 듭니다. 통신 규격 문서처럼 좁고 밀도 높은 도메인이나 복잡한 다단계 추론에서는 GraphRAG가 앞선다는 결과도 전합니다. 온톨로지스트 Kurt Cagle과 Chloe Shannon은 그래프 덩어리를 통째로 컨텍스트 창에 밀어 넣는 실패를 경계하고, Tomas Peluritis는 합의된 지표 정의·문서화된 규칙·소유권·테스트·접근 정책 없이 semantic layer를 올리면 아주 자신만만한 오답 기계가 된다며 진짜 위험으로 오해석을 꼽습니다. 필자의 잠정적 판단 기준은 코퍼스가 하나고 권한 구조가 단순하며 질의응답만 한다면 잘 설계한 RAG로 충분하고, 여러 소스에서 정합성·관계·권한·출처·최신성이 반복해서 문제가 되면 검색기 튜닝으로는 풀리지 않는다는 것입니다.

왜 지금

필자 정현우의 글이 관측한 인기 풀에 오른 것은 이번이 처음으로, 10월 20일 게재 뒤 이번 주 8위(조회수 7,211)로 들어와 처음 분석합니다. 주제로는 W41에 분석해 plan으로 분류한 김영욱의 3951(어노테이션·시맨틱 레이어·온톨로지)과 이어지지만, 이 글은 벤더 제품과 RAG·MCP로 짜인 AI 시스템의 지식 구조 자체가 주제라 ai로 분류했고, 필자의 색인 규칙과 MCP 서버 구현이 비중 있게 실려 develop을 보조 축으로 두었습니다. 키워드로는 해시태그 'RAG'에 근거한 rag가 분류 체계에 키로만 등록돼 있다가 이 글에서 처음 카드에 붙습니다. 'MCP'는 스펙의 범위와 필자의 서버 규칙을 한 절로 다뤄 mcp(W44까지 5회/고유 기사 5건, 마지막 W44 3992)로 묶었고, '지식계층'·'GraphRAG'·'지식그래프'로는 새 키를 만들지 않았습니다.

실무 시사점

이 글이 건네는 첫 도구는 오답의 원인을 두 갈래로 가르는 눈입니다. 맞는 문서를 못 찾은 것인지, 찾기는 했는데 그 문서가 낡았거나 팀마다 정의가 달랐거나 질문자가 봐서는 안 되는 것이었는지를 나누지 않으면, 필자가 검색 관련도를 올리는 것만으로는 풀리지 않는다고 한 문제를 검색 튜닝으로만 붙잡게 됩니다. 사내 RAG 평가표에 검색 적중과 별도로 네 가지 항목을 따로 두면 어느 쪽에서 틀렸는지가 드러납니다. 둘째로 에이전트 도입은 권한과 최신성 판단을 사람의 검수에서 시스템 설계 쪽으로 옮깁니다. 사람이 날짜를 보고 넘기던 판단이 빠지면 Glean 사례처럼 권한도 크롤 지연만큼 낡을 수 있다는 사실까지 설계에 들어와야 하고, MCP로 연결했다고 그 판단이 저절로 생기지는 않습니다. 도구가 둘뿐인 필자의 서버에도 입력 범위 강제와 명시적 오류 같은 규칙이 필요했다는 대목은, MCP 서버를 내놓는 팀이 연결 이후의 책임을 서버 코드로 떠안게 된다는 뜻으로 읽힙니다. 셋째로 W41의 3951과 나란히 놓으면 두 글의 자리가 갈립니다. 3951이 데이터에 의미를 얹는 층을 다뤘다면 이 글은 검색 결과를 믿을 수 있게 만드는 층을 다루고, 3951이 강조한 지표 정의의 일치는 이 글의 네 가지 가운데 주로 정합성에 닿습니다. 지표와 온톨로지를 적는 형식을 하나로 모으는 Apache Ossie도 검색·권한·최신성은 범위 밖에 두므로, 지표 정의를 한 곳에 모은 팀이라도 최신성·권한·출처는 별도 점검 대상으로 남습니다. 필자가 정합성의 첫걸음을 온톨로지 이전의 한글 조사 처리에서 잡은 것도 의미 층보다 더 아래에 손볼 곳이 있다는 신호입니다. 넷째로 Peluritis가 말하는 오해석은 진짜 데이터로 질문을 잘못 알아들은 답이라 출처를 붙여도 그대로 통과하므로, 답변에 출처가 붙었다는 사실만으로 검수를 끝내면 놓치게 됩니다. 근거 쪽에서 짚어 둘 것도 있습니다. 필자의 구현은 사내 시스템을 흐름만 남긴 의사코드와 서술로 전해져 규모나 성능 수치가 없고, Uber의 27%·60%는 필자가 밝히듯 절대값이 아닌 상대 개선치이며 보안·프라이버시 정책 문서 40여 건과 골든 질의 100여 건을 내부 전문가가 평가한 자체 측정 결과입니다. AWS 참조 아키텍처가 판매 구성이기도 하다는 지적과 RAG가 구현 기법 쪽으로 내려간다는 판단은 필자 스스로 사견으로 밝혔고, MCP 스펙의 개정 내용과 Ossie의 인큐베이팅 단계는 10월 20일 게재 시점 기준입니다.

실무 적용 포인트

  • 사내 문서 검색이나 RAG 챗봇을 운영 중이라면 권한이 서로 다른 계정 두 개로 같은 질문을 던지고, 한쪽이 볼 수 없어야 할 문서가 검색 후보 단계에서 이미 빠지는지 답변 직전에야 걸러지는지 로그로 확인합니다. 후보 단계에서 빠지지 않으면 SSO 신원 기준 필터를 검색 질의 쪽으로 옮기는 작업을 백로그 맨 위에 올립니다.
  • 평가용 골든셋에 색인 안에 답이 없는 질문을 일부러 섞고, 그 질문에는 없다고 답해야 맞는 것으로 채점 기준을 고칩니다. 이후 튜닝에서 전체 정확도가 올랐더라도 이 항목 점수가 떨어졌다면 그 변경은 되돌릴 후보로 분류합니다.
  • 한국어 문서를 색인하는 검색은 '연차가'와 '연차는'처럼 조사만 다른 질의 쌍을 자주 묻는 용어마다 만들어 결과가 같은 문서를 가리키는지 확인합니다. 갈리는 쌍이 나오면 임베딩 모델을 바꾸기 전에 질의 쪽 접두사 확장과 색인·질의 양쪽의 bigram 분절을 넣는 안부터 검토합니다.

핵심 용어

지식 계층(Knowledge Layer) 필자가 특정 제품이 아닌 역할 이름으로 쓰는 말로, AI가 여러 지식원 위에서 의미·관계·검색·권한·출처·최신성을 함께 고려해 지식을 쓸 수 있게 해 주는 중간 계층을 가리킵니다. 같은 단어라도 회사마다 범위가 달라, AWS는 문서 청킹과 벡터 검색을 Data Layer 소관으로 두는 반면 마이크로소프트는 청킹과 임베딩을 Foundry IQ의 능력으로 열거합니다.오해석(misinterpretation) 데이터는 진짜인데 질문을 잘못 알아듣고 답하는 실패로, 모델이 없는 사실을 지어내는 환각과 구별됩니다. 필자가 인용한 Tomas Peluritis가 환각 대신 진짜 위험으로 꼽은 것이고, 필자는 앞서 든 활성 고객 예로 돌아가 무료 체험 계정까지 넣어 센 숫자를 '활성 고객 수'라고 정확히 계산해 주는 경우를 듭니다. 숫자 자체에는 틀린 데가 없어 받아 보는 사람도 검수자도 잘못을 바로 알아채기 어렵다는 것이 필자의 설명입니다.한글 bigram 분절 한글 문장을 두 글자 단위로 쪼개 색인과 질의 양쪽에 넣는 방식입니다. 조사가 앞뒤 어디에 붙어도 원형 토큰의 bigram이 살아남아, 색인에는 '연차는'이 있고 사용자는 '연차가'로 물어도 둘 다 '연차'라는 bigram으로 만납니다. 필자는 세 글자 이상 원형 토큰은 질의 토큰 끝 한두 글자를 잘라 와일드카드를 붙이는 접두사 확장이 잡고, 그것이 놓치는 두 글자 조사나 색인 쪽에 조사가 붙은 경우를 bigram이 메우도록 둘을 병행했습니다.

  • 필자는 처음의 '웹에서 SQL을 연습할 수 있게 하자'는 생각을 구현 단계에서 네 가지 조건으로 바꿨습니다. 별도의 DBMS를 설치하지 않을 것, 서버 상태와 무관하게 같은 데이터셋으로 바로 연습할 것, JOIN과 GROUP BY가 의미 있게 동작하도록 관계와 분포가 있는 데이터를 갖출 것, 같은 결과를 만드는 여러 SQL을 정답으로 인정할 것입니다. 이 조건을 정하자 SQL 실행은 브라우저에서 처리하고, 여러 기기에서 이어 봐야 하는 학습 진도·사용자 설정과 커뮤니티 글처럼 저장이 필요한 데이터만 클라우드에 두는 구분이 나왔다고 합니다. 필자는 이를 '어떤 기술을 쓸까'보다 '사용자가 첫 쿼리까지 몇 단계를 거쳐야 할까'를 먼저 기준으로 삼은 결정이라고 설명합니다.
  • SQL 실행에는 SQLite를 웹어셈블리로 컴파일한 sql.js를 써서, 입력한 쿼리를 실행 서버로 보내지 않고 브라우저 메모리에 올라온 SQLite에서 처리합니다. 계정이나 DB 접속 정보가 필요 없고, 서버에 사용자별 실습 DB를 만들고 정리하는 운영 부담이 줄며, 잘못된 UPDATE·DELETE도 다른 사용자 데이터에 닿지 않습니다.
