핵심 포인트

  • 필자는 VSCode 터미널에서 클로드 코드나 코덱스를 실행해 에이전트가 파일을 고치는 과정을 편집기로 보며 써 왔는데, 에이전트 구독을 두 개로 늘린 뒤 터미널을 하나 더 열자 두 에이전트가 같은 작업 디렉터리를 보고 한쪽이 고치는 파일을 다른 쪽도 읽게 됐습니다. 브랜치도 하나뿐이라 두 작업의 변경 사항이 한곳에 섞였고, 커밋하려면 어느 줄이 어느 작업의 결과인지 되짚어야 했습니다. 여러 에이전트로 병렬 작업을 하기 좋은 도구를 찾다 오르카를 알게 돼 최근 2주 반 동안 옮겨 쓰고 있으며, 글은 코덱스와 클로드 두 에이전트를 함께 쓰는 사람의 기준으로 썼다고 밝힙니다. 필자는 오르카가 새 AI 모델이 아니라 쓰던 에이전트를 어디에 담아 둘지 바꾸는 오픈소스 도구라서 구독을 늘리지 않고 쓰던 계정을 연결하면 된다고 설명하고, 자신은 클로드와 코덱스 계정을 하나씩 등록해 작업에 따라 고릅니다.
  • VSCode 시절 반복된 불편은 네 가지였습니다. 한쪽에서 이미 고쳐 둔 내용이 있는데도 다른 에이전트가 그 이전 상태를 기준으로 판단해 엉뚱한 답을 내놓는 일이 있었고, 폴더가 하나라 브랜치를 바꾸려면 작업 중인 내용을 먼저 치워야 해서 에이전트가 파일을 고치는 중이면 끝나기를 기다렸다가 옮겨야 했습니다. 필자는 그 결과 동시에 진행한다고 생각한 두 작업이 실제로는 번갈아 진행하는 형태가 됐다고 적습니다. 터미널이 두세 개로 늘면 탭 이름만으로는 어느 탭이 무슨 작업인지 구분되지 않았고, 보고 있는 답변이 코덱스와 클로드 중 어느 쪽 것인지는 출력을 한참 올려 보고서야 알았으며, 아직 일하는 중인지 알려면 탭을 하나씩 눌러 마지막 출력을 읽어야 해 이미 끝난 작업을 한참 뒤에 확인하기도 했습니다. 코덱스를 얼마나 썼고 언제 다시 채워지는지, 클로드는 얼마나 남았는지도 작업할 때마다 따로 확인해야 해서 나중에는 확인을 미루고 어느 에이전트에게 줄지를 감으로 정했습니다.
  • 필자는 도구를 바꾸며 기능이 늘어난 것보다 작업을 나누는 단위가 달라진 쪽이 더 크게 느껴졌다고 말합니다. 작업을 만들 때 필자가 하는 일은 이름을 정하고 붙일 에이전트를 고르는 데까지이고, 오르카가 그 작업 몫의 워크트리와 브랜치를 만들어 주므로 git 명령을 직접 치지 않습니다. 예전에는 금방 끝날 일에 브랜치까지 만드는 것이 번거로워 쓰던 브랜치에서 이어 가곤 했지만 이제는 그럴 일이 없어졌고, 작업이 끝나면 워크트리를 통째로 정리하거나 결과를 더 봐야 하면 남겨 둡니다. 브랜치를 지우고 폴더를 되돌리는 일을 따로 하지 않아도 돼 끝내는 것도 시작만큼 가벼워졌다고 합니다. 검토할 때는 그 워크트리의 diff만 보면 돼 다른 작업의 수정이 섞이지 않고, 결과가 마음에 들지 않으면 어느 줄이 어느 작업의 것인지 가려낼 필요 없이 해당 워크트리를 삭제하면 됩니다.
  • 확인하는 습관도 바뀌었습니다. 예전에는 작업이 끝났는지 보려고 중간에 몇 번씩 들여다보다 하던 일의 흐름이 끊기거나, 시켜 놓은 사실 자체를 잊기도 했습니다. 오르카는 작업이 끝나면 알림을 보내고 계정을 연결해 두면 휴대폰으로도 같은 알림이 와서, 필자는 오래 걸릴 작업을 맡겨 두고 자리를 떴다가 알림을 받고 돌아와 확인하면 시간을 효율적으로 쓸 수 있다고 말합니다. 휴대폰에서 결과를 훑어보고 이어서 시킬 일이 분명하면 자리로 돌아오기 전에 다음 작업을 걸어 두기도 합니다. 두 계정의 사용량을 한 화면에 보여 줘서, 코덱스가 얼마 남지 않았으면 긴 작업은 클로드로 넘기는 식으로 남은 양을 보고 에이전트를 고를 기준이 생겼다고 적습니다.
  • 필자는 여러 작업을 동시에 시키고 결과를 각각 검토해야 하는 사람, 특히 구독을 두 개 이상 쓰는 사람에게 이점이 크다고 보지만, 에이전트를 하나만 쓴다면 지금 편집기로 충분하다고 말합니다. 확장 프로그램과 단축키, 디버거를 새 환경으로 옮기는 비용이 적지 않으니 에이전트에게 맡기는 일과 직접 쓰는 일의 비중을 먼저 따져 보라고 권합니다. 한계로는 오르카가 빠르게 바뀌는 중이라 쓰는 동안에도 버전이 여러 번 올라 글을 쓸 당시 1.4.205였고 화면 구성이나 기능 이름이 읽는 시점과 다를 수 있다는 점, 작업마다 폴더가 나뉘어 한 작업에서 설치한 의존성이나 만든 설정 파일이 다른 작업에는 없다는 점을 듭니다. 크게 불편했던 점은 아직 없다면서도 굳이 꼽자면 VSCode에서 쓰던 터미널 키퍼처럼 폴더마다 띄울 터미널을 미리 정해 두는 방식이 없어 자주 쓰는 구성을 저장해 불러오지 못한다고 덧붙입니다.

실무 시사점

브랜치(branch) git에서 커밋이 쌓이는 갈래로, 같은 저장소 안에서 서로 다른 작업의 변경 이력을 따로 이어 가게 해 줍니다. 필자가 VSCode에서 두 에이전트를 돌릴 때는 브랜치가 하나뿐이라 두 작업의 변경 사항이 한곳에 섞였고, 커밋할 때 어느 줄이 어느 작업의 결과인지 되짚어야 했습니다. 오르카에서는 작업을 만들 때마다 워크트리와 함께 브랜치가 하나씩 생겨 커밋이 각자의 브랜치에 쌓이므로, 필자는 금방 끝날 일도 쓰던 브랜치에 이어 붙이지 않게 됐다고 말합니다.diff 변경 전과 후의 차이를 줄 단위로 보여 주는 비교 결과입니다. 필자는 오르카에서 변경 사항이 작업별 브랜치에 나뉘어 담기면서, 어떤 작업을 검토할 때 그 워크트리의 diff만 보면 되고 다른 작업의 수정이 섞여 들어오지 않게 됐다고 설명합니다. 결과가 마음에 들지 않을 때도 두 작업이 섞인 변경에서 어느 줄이 어느 작업의 것인지 가려내는 대신 해당 워크트리를 통째로 삭제하면 되어 대처가 간단해졌다고 합니다.의존성(dependency) 프로그램이 돌아가는 데 필요한 외부 라이브러리나 패키지를 말합니다. 오르카는 작업마다 폴더를 따로 두기 때문에 한 작업에서 설치한 의존성이나 만들어 둔 설정 파일이 다른 작업 폴더에는 없습니다. 필자는 이를 작업 단위 분리의 장점이면서 동시에 생각할 거리로 꼽고, 여러 작업에 공통으로 필요한 준비가 있다면 그 부분을 어떻게 공유할지 정해 두는 편이 좋다고 권합니다.

이 사고에서 위험의 크기를 바꾼 것은 모델이나 설치 방식이 아니라 훅 설정의 type 한 줄이었습니다. 필자 설명대로 type: agent 훅이 하네스 안쪽에서 도는 실행에 가까웠다면, claude -p를 부르는 스크립트를 실행한 type: command 훅은 같은 settings.json을 읽는 새 프로세스를 하네스 바깥에 만들었고, 그 순간 훅은 자기 자신을 다시 부를 수 있는 구조가 됐습니다. 그래서 훅을 검토할 때는 그 훅이 무엇을 하는지와 함께 무엇을 새로 띄우는지를 따로 물을 필요가 있습니다. W43에 분석한 3930의 리뷰 루프와 견주면 멈춘다는 말이 두 갈래로 나뉩니다. 3930이 정한 최대 3라운드, 같은 카테고리의 지적이 연속 2라운드 같은 문구로 나오면 blocked로 돌린다는 기준은 일부러 설계한 반복이 언제 수렴했고 언제 사람을 불러야 하는지를 가르는 종료 판정입니다. 반면 이 글의 다섯 원칙 가운데 넷은 훅이 애초에 루프가 되거나 사람 눈 밖으로 나가지 못하게 길을 막는 경계선이고, 남은 비용 상한(최대 실행 횟수·쿨다운)만이 아무도 의도하지 않은 반복이 생겼을 때 그 횟수를 끊는 바닥 장치입니다. 3930에도 종료를 막고 리뷰를 다시 돌리게 하는 remind-review.sh 훅이 있었으니, 훅이 반복에 끼어든다는 점만으로는 두 사례가 갈리지 않습니다. 갈림길은 그 반복에 횟수 상한이 적혀 있느냐로, 3930은 리뷰 루프에 3라운드 상한을 적어 두었지만 이 글의 훅에는 필자 말대로 그런 장치가 아예 없었습니다. W41 3906의 Anvil은 claude -p로 클로드 코드를 불러도 평소의 훅을 그대로 통과하게 만든 점을 장점으로 삼았는데, 이 사고에서는 바로 그 성질이 재귀의 통로였습니다. 훅이 띄운 세션도 같은 프로젝트 폴더와 settings.json을 로드해 같은 SessionEnd 훅을 탔기 때문에, 스크립트나 봇에서 클로드 코드를 헤드리스로 부르는 팀이라면 그 호출이 어떤 종료 계열 훅을 물려받는지도 점검 범위에 넣는 편이 안전합니다. W40·W42 3931처럼 폴더마다 .claude를 따로 두는 구성이라면 이런 훅이 숨어 있을 settings 파일도 폴더 수만큼 늘어나니, settings 파일을 코드만큼 조심해서 다루라는 필자의 말을 지키려면 점검 범위도 폴더 단위로 넓혀야 합니다. W45 3993은 캐시를 살려 한도를 아끼는 습관을 다뤘습니다. 이 글의 7월 2일 사용량은 대부분이 캐시 읽기였으니 캐시는 오히려 잘 재사용되고 있었는데도, 이튿날 오전 세션 한도에 걸렸습니다. 캐시 읽기가 세션 한도에 얼마만큼 잡히는지는 본문에 나오지 않지만, 캐시 습관이 줄이는 것은 세션 하나가 쓰는 양이고 세션 수가 저절로 불어나는 구조는 그 바깥의 문제입니다. 이 글은 한 사람의 macOS 환경에서 겪은 사고 한 건의 복기라, 이상 사용량이 전날부터 쌓였다는 판단과 파인더의 CPU 점유가 2차 효과라는 설명은 필자의 추정이고 1단계의 type: agent 훅만으로도 재귀가 생겼을지는 확인되지 않았습니다. 비용 상한은 원칙으로만 제시돼 구현 예시가 없으며, SessionEnd 훅·type 값·claude -p 같은 설정과 세션 한도는 사고가 난 7월 1~3일과 글이 게재된 9월 28일 시점의 클로드 코드 기준이고, Sonnet 5도 사고 당시 새로 나온 모델로 언급된 이름입니다. 글 끝에는 AI의 도움을 받아 작성했다는 고지가 있습니다.

실무 적용 포인트

  • 프로젝트의 .claude와 사용자 전역 ~/.claude의 settings 파일에서 SessionEnd처럼 끝나는 시점에 붙은 훅을 모두 찾고, 각 훅이 실행하는 스크립트까지 열어 claude를 다시 부르거나 nohup·&·disown으로 프로세스를 떼어 내는 줄이 있는지 확인합니다. 폴더마다 .claude를 따로 둔 구성이면 필자의 rg 명령을 폴더별로 돌리고, rg가 기본으로 건너뛰는 .gitignore 대상·숨김 파일까지 보도록 -uu를 붙인 결과와 맞대어 빠진 설정 파일이 없는지 비교합니다.
  • 세션 종료 때 LLM에게 정리나 동기화를 시키는 훅이 있으면 그 지시문을 커맨드나 스킬로 옮기고, 훅은 정리할 일이 생겼다는 표시를 타임스탬프와 함께 파일에 남기는 일만 하도록 줄입니다. 다음 세션을 열었을 때 그 표시가 보이면 직접 명령을 불러 정리를 실행합니다.
  • LLM을 자동으로 부르는 스크립트를 끝내 남겨야 한다면 맨 앞에 실행 기록 파일을 읽는 검사를 넣어, 직전 실행 뒤 쿨다운이 지나지 않았거나 하루 실행 횟수가 정한 상한을 넘었을 때는 곧바로 빠져나오게 합니다. 훅 설정을 바꾼 날에는 세션을 하나 열었다 닫은 뒤 프로세스 목록에 claude 프로세스가 저절로 떠 있지 않은지, 세션 로그 폴더에 직접 열지 않은 세션이 새로 생기지 않는지 살펴봅니다.

핵심 용어

멈추는 규칙(stopping rule) 필자가 루프를 이루는 요소로 트리거·목표·검증과 함께 꼽은 종료 조건입니다. 테스트가 모두 통과하면 멈추거나 재시도를 최대 5번까지만 하는 식의 조건이 반복 구조에는 설계 단계부터 들어가며, 어디서 멈출지 정하지 않으면 루프 자체가 성립하지 않는다고 필자는 봅니다. 훅은 정해진 시점에 한 번 실행하고 끝나는 것이 정상이라 이 규칙을 따로 두지 않는데, 훅이 새 세션을 낳아 반복되기 시작하면 루프의 형태만 갖추고 이 규칙은 빠진 상태가 됩니다.command 훅과 agent 훅(type: command / type: agent) 클로드 코드 훅 설정에서 type 값으로 갈리는 두 실행 방식입니다. 필자에 따르면 type: agent는 훅 시점에 LLM 에이전트를 돌리는 방식이라 세션이 끝날 때마다 에이전트가 돈다는 점에서 좀 위험하긴 해도 하네스 안쪽에서 도는 실행에 가깝고, type: command는 지정한 명령을 실행합니다. 이 사고에서는 command가 실행한 session-end-sync.sh가 claude -p로 새 CLI 프로세스를 띄우면서 훅이 새 세션 생성기로 바뀌었습니다. 설정 이름은 사고가 난 7월과 9월 28일 게재 시점 필자 환경의 클로드 코드 기준입니다.결정적 작업(deterministic task) 같은 입력이면 늘 같은 결과를 내고 짧게 끝나는 작업입니다. 필자는 로그 남기기, 타임스탬프 찍기, 정적 파일 검사처럼 이런 작업만 훅에서 돌리고, 비용·시간·실패·재시도·컨텍스트 로딩이 딸려 오는 LLM 호출은 훅에 넣지 말라고 말합니다.
